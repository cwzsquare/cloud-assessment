## 实现落点总览

当前这 15 个三级模块并不是散落实现，而是走同一条链路：

1. 采集：
   [collector.py](/root/cloud-assessment/apps/api/cloudnative_security/collector.py:431) 从 `manifest`、`kubeconfig` 或 `PVE SSH -> control-plane VM` 采集 Kubernetes、control-plane、auth.log、Falco/Trivy/Kyverno 证据。
2. 适配：
   [adapters.py](/root/cloud-assessment/apps/api/cloudnative_security/adapters.py:131) 的 `CloudNativeAdapter` 负责把采集结果送入规则引擎。
3. 规则：
   [rules.py](/root/cloud-assessment/apps/api/cloudnative_security/rules.py:1732) 负责输出带证据和整改建议的 `Finding`。
4. 汇总：
   [orchestrator.py](/root/cloud-assessment/apps/api/cloudnative_security/orchestrator.py:240) 负责归一化、数据质量、评分和报告。
5. 展示：
   [server.py](/root/cloud-assessment/apps/api/cloudnative_security/server.py:277) 提供 API，前端页面来自 [index.html](/root/cloud-assessment/apps/web/static/index.html:1) 和 [app.js](/root/cloud-assessment/apps/web/static/app.js:1)。

## 当前结论

- 从“标书三级模块是否已有实现”看：`15/15` 已有实现。
- 从“当前正向样例 live 扫描结果”看：大部分模块能稳定产出证据，当前主要残留集中在：
  - `CN-6`：`orders-db` 缺 `HPA/PDB`
  - `CN-30`：环境中仍能识别异常登录证据
  - `CN-36`：实验环境 `hostPath` PV 与备份证据不足
  - `CN-37`：有状态工作负载缺少绑定的备份/快照证据
  - `CN-38`：真实 registry API 仍未接入，只是原型能力完整
